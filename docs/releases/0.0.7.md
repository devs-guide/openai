## 0.0.7

DOT agents now preserve work through verified persistent checkpoints and keep
authorized projects moving through one evidence-based health monitor. The
Agent saves and reads back work as it is produced, detects avoidable inactivity
without mistaking slow or blocked work for failure, and recovers from the last
verified state.

Research projects also gain immutable ZIP checkpoints, complete Markdown data
views beside canonical CSV/JSON pairs, and need-based functional storage such
as `agent:pdf`. These behaviors ship together so no partial storage or progress
contract is released early.

### Scope

- Release range: `0.0.6..0.0.7`.
- Product boundary: DOT Agent persistence/progress and Research recovery/data
  integration.
- Published entrypoints: Agent, Storage, Progress, Browser, Project, Internet,
  Data, Template, Summary, configuration, schema, feature, and release routes.
- Included release identity: DOT `0.0.7`, prior release `0.0.6`, migration
  baseline `0.0.1`.
- Excluded: starting an actual project schedule, creating a real storage
  location during release publication, running a Research topic, changing
  model selection, changing `BROWSER-004`, attaching generated artifacts, or
  granting new recipients, permissions, deletion, Codex, or software work.

### Highlights

- Defines required `#STORAGE` and `#FILES` controls for verified persistence,
  recovery manifests, capacity, archives, and delivery evidence.
- Defines required `#PROGRESS` and evidence-based `#LAZY` recovery for the
  complete project rather than Browser state alone.
- Uses one verified 15-minute cron-style monitor when supported and authorized,
  with truthful event-driven fallback and no overlapping project run.
- Allows need-based shared `agent:<term>` locations or Projects while keeping
  WIP storage, final delivery, access, sharing, and deletion separate.
- Packages every completed Research batch or interruption checkpoint as an
  immutable, readback-verified ZIP successor.

### Added

- `STORAGE-001` through `STORAGE-012` and `PROGRESS-001` through
  `PROGRESS-008`.
- Destination registry, artifact preservation, recovery manifest, health
  check, consultation, capacity, and archive manifest Templates.
- Agent configuration schema v3 with `agent:storage`, purpose-location rules,
  archive verification, central health checks, cron metadata, and `#LAZY`
  classification controls.
- Acceptance coverage for scheduling, overlap, stalls, storage failure,
  provisioning, delivery, substantive research, archive integrity, data
  parity, security, and project lifecycle cases.

### Changed

- Browser Tabs now consumes the project-wide Progress monitor instead of
  defining an independent schedule; the four-tab behavior remains intact.
- Project, Internet, Data, Page, and Summary require verified persistent inputs
  and register their outputs before dependent work or review.
- Each applicable Data basename retains its CSV/JSON machine pair and adds a
  complete readable Markdown view from the same logical records.
- Advanced ingestion, Pages, workflow, feature, and release metadata to
  `0.0.7`, with `0.0.6` as the immediate predecessor.

### Fixed

- Prevented plans, open tabs, repeated blockers, and unsaved generated files
  from being counted as substantive progress.
- Prevented a slow healthy action, authorized wait, or genuine external
  dependency from being mislabeled `#LAZY`.
- Prevented local paths, upload acknowledgements, filenames, or WIP locations
  from being presented as verified persistence or delivery.
- Prevented duplicate purpose locations, overlapping monitors, self-hashing
  archives, silent overwrites, and compression-driven deletion.

### Operator workflow and safety

Verify the persistent destination with a save/reopen probe before substantive
work. Save each useful artifact immediately, update the recovery manifest, and
create a Research ZIP successor at every completed batch or interruption
checkpoint. Create or reuse an `agent:<term>` location only when capacity,
format, or separation requires it; creation never grants sharing, publication,
permission changes, deletion, or final-delivery status.

When authorized scheduling exists, verify the Project ID, schedule ID,
timezone, enabled state, and next run. Otherwise use the declared event-driven
checks. Routine all-clear results remain in the persistent log; only meaningful
progress, blockers, decisions, or missed commitments notify the owner.

### Interfaces and compatibility

- `dot-agent/2`, `dot-agent-config/3`, `dot-research-project/2`,
  `dot-research-data/2`, and `dot-research-summary/3` supersede their prior
  contract versions for new `0.0.7` activations.
- `agent:storage` is the default identifier but never proof of access,
  persistence, or capacity. Project-approved overrides remain supported.
- `agent:<term>` names use lowercase action/outcome terms and are shared by
  function with Project-level artifact separation.
- The current model/fallback order, runtime observations, four-tab default,
  Research sequence, and intentional `BROWSER-004` behavior remain compatible.

### Migration and recovery

Existing work must first identify and read back its latest verified artifact.
The Agent creates a versioned recovery manifest rather than relabeling local or
historical material as preserved. Reconstructed records remain distinct from
newly revalidated records. Accepted dataset releases and prior verified
archives remain immutable; changes create successors.

### Validation evidence

GitHub Actions must verify canonical rule ownership, exact configuration,
unchanged models and CAPTCHA behavior, scheduling and `#LAZY` cases, storage
and provisioning cases, archive integrity, CSV/JSON/Markdown parity, complete
publication routes, and the single frozen edge-case ledger. No local build,
compile, formatting, or test result is used as release evidence.

### Known boundaries

- The contract cannot create a scheduler or persistent destination unless the
  active runtime exposes and authorizes that operation.
- The owner-stated single-Agent-per-account condition is dated context, so
  leases still protect against worker and scheduled-run overlap.
- Local-only work during a storage outage remains incomplete and at risk.
- The release defines recovery behavior; it does not claim a later real-world
  project, schedule, archive upload, or recipient access test succeeded.
