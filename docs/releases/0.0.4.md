## 0.0.4

The repository adds one reusable `#RELEASE` contract for planning, writing,
reviewing, publishing, correcting, and handing off GitHub releases across all
current and future products. Release notes now use a compact reader-focused
core and add operator, interface, migration, evidence, or boundary sections
only when the release actually needs them.

This release also completes the publication chain needed for the first manual
full-project test of the DOT Agent and Research package. The manual test remains
separate from repository publication and starts from the immutable `0.0.4`
source archive and `dot/ingest.json`.

### Scope

- Release range: `0.0.3..0.0.4`.
- Repository-wide contract: `docs/release.prompt`.
- Published entrypoints: `/release/`, `/raw/docs/release.prompt`, and the
  existing DOT documentation and raw-source routes.
- Included release identity: DOT `0.0.4`, prior release `0.0.3`, migration
  baseline `0.0.1`.
- Excluded: executing the later manual Agent research test, changing Agent
  models or permissions, changing `BROWSER-004`, and attaching binary assets.

### Highlights

- Establishes a single repository-wide release voice without turning release
  notes into DOT runtime instructions.
- Requires complete release-range review, exact commit history, explicit scope,
  accurate asset descriptions, and reader-focused outcomes.
- Uses an adaptive format: a compact required core plus conditional sections
  for workflows, safety, interfaces, migration, evidence, and known boundaries.
- Requires stacked releases to publish sequentially before dependent pull
  requests advance.
- Adds an exact immutable-archive handoff for a separate manual Agent test.

### Added

- `docs/release.prompt` with `RELEASE-001` through `RELEASE-010`.
- Rendered and byte-exact raw Pages routes for the Release contract.
- Repository and Pages validation for Release ownership, structure, adaptive
  modules, routes, version identity, and publication safeguards.
- A reviewed `0.0.4` record and release-workflow identity.

### Changed

- Extended root, feature, and release navigation to cover the repository-wide
  Release contract.
- Advanced DOT ingestion metadata to `0.0.4` while retaining `0.0.1` as the
  immutable baseline and `0.0.3` as the immediate predecessor.
- Generalized predecessor validation so every supported post-baseline release
  requires its predecessor's annotated tag and published GitHub Release.
- Extended remote Pages validation to the Release contract and `0.0.4` record.

### Fixed

- Prevented release narratives from treating one deployment or private
  operational detail as universal project behavior.
- Prevented optional long-form release sections from becoming mandatory filler.
- Required live release verification to include target commit and prerelease
  state in addition to title, body, tag, draft state, and assets.
- Rejected every obsolete candidate-version reference while preserving `0.0.1` as the first
  published migration baseline.

### Safety and publication model

The Release contract does not authorize a merge, tag, upload, publication,
external announcement, or downstream Agent task. Those actions retain their
separate owner and GitHub workflow gates.

Published tags and target commits are immutable. Behavioral corrections use a
later version. GitHub release bodies may be corrected only through a separately
reviewed exact replacement that leaves the tag, target, state, and assets
unchanged.

Compilation, contract auditing, Pages builds, and release verification remain
GitHub Actions-only. The later full-project Agent test is manual and is not a
condition for publishing this repository release.

### Interfaces and compatibility

- New canonical prompt: `docs/release.prompt`.
- Rendered route: `https://devs-guide.github.io/openai/release/`.
- Raw route: `https://devs-guide.github.io/openai/raw/docs/release.prompt`.
- Release workflow input remains the bare semantic version, exact 40-character
  `main` SHA, `draft` or `publish` mode, and exact confirmation string.
- DOT instruction order, conditional activation, model configuration, browser
  behavior, and Research workflow remain compatible with `0.0.3`.

### Validation evidence

GitHub Actions must verify repository source, prompt rule ownership, the DOT
migration audit, the publication manifest, rendered and raw routes, live Pages
source identity, reviewed release notes, predecessor publication, and the final
GitHub release state against the same exact commit.

### Known boundaries

- `#RELEASE` governs GitHub repository releases; `#DATA` continues to govern
  immutable research dataset releases.
- Release documentation cannot establish that a later manual Agent test
  succeeded.
- GitHub-generated source archives are the only release assets; no generated
  PDF, application, database, or binary is attached.
