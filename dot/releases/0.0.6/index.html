0.0.6

DOT agents now coordinate browser tabs as one shared resource instead of treating each window or worker as an independent browser. Projects start with a four-tab default, may record another approved positive limit, and preserve a resumable queue when capacity is full.

Long-running browser work also gains a truthful monitoring branch: use a verified 15-minute recurring check when scheduling is available and authorized, or disclose the limitation and use event-driven checks. The release does not change model selection, research authority, or CAPTCHA behavior.

Scope

  • Release range: 0.0.5..0.0.6.
  • Product boundary: DOT Agent configuration and the Browser capability module.
  • Published entrypoints: Agent, Browser, configuration, schema, feature, and release rendered and raw routes.
  • Included release identity: DOT 0.0.6, prior release 0.0.5, migration baseline 0.0.1.
  • Excluded: opening real browser sessions, running a Research project, changing model selection or fallback order, changing BROWSER-004, and attaching generated or binary assets.

Highlights

  • Defines #TABS as the Browser-owned configuration for shared capacity, ownership, queues, monitoring, and recovery.
  • Applies one effective limit across all Agent-controlled windows and workers, with four tabs as the configured default.
  • Prevents capacity races and unsafe closure of authentication, unsaved-form, download, takeover, or leased tab state.
  • Makes scheduled and event-driven blocker monitoring explicit alternatives so unavailable automation is never reported as active.

Added

  • Agent configuration schema v2 with required Browser tab defaults, shared scope, project-override policy, and blocker-check branch.
  • TABS-001 through TABS-007 for inventory, leases, queuing, checkpoints, monitoring, recovery, notifications, pause, and cleanup.
  • Acceptance checks for shared-cap enforcement, worker contention, unknown inventories, protected tabs, scheduling fallback, and sensitive-state exclusion.

Changed

  • Extended Agent preflight and portable checkpoints with the effective tab limit, inventory, ownership, queue, and monitoring mode.
  • Updated Browser preflight to use configured tab controls while retaining its existing source, access, failure, and CAPTCHA responsibilities.
  • Advanced ingestion, Pages, workflow, feature, and release metadata to 0.0.6, with 0.0.5 as the immediate predecessor.

Fixed

  • Prevented separate workers or windows from each interpreting the tab limit as their own allowance.
  • Prevented an unknown global inventory from being treated as unused capacity.
  • Prevented an uncreated, unauthorized, failed, or unverified recurring check from being described as active monitoring.
  • Prevented generic failures from being attributed to memory, CPU, the browser, or a website without observed evidence.

Operator workflow and safety

Before browser work, record the configured default, any approved project override, the effective shared limit, and the observable inventory. Reserve a slot before opening a tab; at capacity, safely reuse a tab or queue the work. Checkpoint useful state before handoff or closure and exclude credentials, tokens, private URLs, and sensitive authentication routes from portable logs.

If an authorized recurring scheduler is available, create and verify the 15-minute check. Otherwise use the named event-driven triggers and report that no recurring automation exists. Pausing or ending the project also pauses or removes its schedule and records the final tab and queue disposition.

Interfaces and compatibility

  • dot-agent-config/2 supersedes version 1 for new 0.0.6 activations and requires browser.tabs.
  • default_max_open is 4; an owner-approved Project Control Packet may set another positive integer for that project without changing the canonical configuration.
  • limit_scope is ALL_WINDOWS_AND_WORKERS. User-navigable document tabs and popup windows count; browser chrome and non-tab modal UI do not.
  • Existing #BROWSER, #TOOL, and #CAPTCHA names remain valid. #TABS is embedded in browser.prompt, so there is no separate Tabs prompt or route.

Validation evidence

GitHub Actions must verify configuration v2, the complete TABS-001 through TABS-007 rule set, shared-cap and monitoring scenarios, unique canonical clauses, exact ingestion hashes, rendered and raw Pages sources, unchanged model selection and fallback order, unchanged runtime observations, and the approved byte-exact BROWSER-004 behavior.

Known boundaries

  • The contract coordinates the browser surfaces and scheduling capabilities actually exposed to the Agent; it does not create tabs, workers, or a scheduler that the runtime does not provide.
  • A configured project limit is an operating bound, not evidence of available memory, CPU, browser stability, or website capacity.
  • This release defines and validates the workflow. It does not claim a later real-world browser or Research project succeeded.
